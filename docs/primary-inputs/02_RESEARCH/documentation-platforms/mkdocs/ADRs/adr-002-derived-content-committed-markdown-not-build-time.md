# ADR-002: AI-derived content is committed Markdown via PR; build-time generation reserved for mechanical views

## Status
Proposed

## Context
The ecosystem requires AI-derived views (recruiter pages, interview-prep sections, role-specific docs) to be separated from canonical content, validated, PR-reviewed, and regenerated incrementally. MkDocs offers two generation patterns: (a) ordinary files committed to the repo, and (b) virtual files created at build time via `mkdocs-gen-files` (`on_files` event) with nav stitched by `mkdocs-literate-nav`. Build-time generation would let the AI run inside the build — but then the rendered content never appears in a diff, defeating PR review, and would couple builds to AI provider availability, violating the static-first rule.

## Decision
1. AI-derived prose is generated by CI jobs (provider-abstracted scripts), written as Markdown into `docs/derived/**` with frontmatter marking provenance (`generated: true`, `source_hash`, `model`, `generated_at`), and proposed via PR.
2. `mkdocs-gen-files` + `mkdocs-literate-nav` are used only for mechanical, deterministic views: tag indexes, per-role landing pages assembled from frontmatter, nav summaries.
3. Incremental regeneration is driven by comparing `source_hash` frontmatter against current canonical file hashes in the CI job — MkDocs itself always performs a full (fast) build.
4. `mkdocs build --strict` plus a validation hook gate every PR containing derived content.

## Consequences
- Every AI output is visible in a diff and reviewable; provenance is machine-checkable via frontmatter.
- Builds are deterministic and AI-independent; the published site never depends on a provider being up.
- The repo carries generated files (acceptable noise; isolated under `docs/derived/`), and CI must manage regeneration PRs.

## Alternatives
- **All generation at build time via gen-files**: cleaner repo, but removes PR review of rendered content and makes builds depend on AI — rejected.
- **Separate derived-content repo**: stronger separation but doubles operational surface for one engineer — rejected as overengineering.
